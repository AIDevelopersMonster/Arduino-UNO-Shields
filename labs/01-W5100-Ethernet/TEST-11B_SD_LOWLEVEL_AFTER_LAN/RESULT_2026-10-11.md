# TEST-11B — Sd2Card low-level init after LAN: observed result

**Date:** 2026-10-11  
**Status:** **VALID SD BASELINE / LAN STAGE STALLS**

Observed sequence:

```text
C
C init=PASS ms=304 error=0x00 NONE data=0x00 type=3
C
C init=PASS ms=4 error=0x00 NONE data=0x00 type=3
L1
L1 prepareLAN: OK
L1 W5100 soft reset: PASS
```

No later `L1 LAN PASS` or `L1 DHCP: FAIL` was observed. Subsequent typed commands (`L0`, `C`, `R`, ...) produced no responses because the sketch had not returned to its command loop.

## What this establishes

- The low-level Arduino `Sd2Card::init()` baseline is valid and repeatable before LAN.
- SDHC card type 3 was detected twice with native error code 0.
- Raw W5100 MR software reset still succeeds after the SD low-level initialization.
- The sketch then stalls somewhere after that point inside the normal Ethernet startup path, before it can print the result of `Ethernet.begin(...)`.

This run does **not** test SD after LAN because LAN startup never returned and `L0` was never executed.

## Next isolation step

Before adding another full network test, use the existing command set after a fresh AVR reset:

```text
C
R
C
```

If both C probes pass, raw W5100 reset alone does not poison subsequent SD initialization. The remaining fault boundary then lies inside later Ethernet/W5100 initialization or socket/DHCP activity.


## Additional-power run

The operator repeated TEST-11B with additional power connected. The behavior inverted relative to the earlier run:

```text
C
C init=FAIL ms=2005 error=0x01 CMD0 data=0xFF
C
C init=FAIL ms=2004 error=0x01 CMD0 data=0xFF
L1
L1 prepareLAN: OK
L1 W5100 soft reset: PASS
L1 LAN PASS IP=192.168.1.79
UDP=5006
L0
L0 UDP stop + LAN release: DONE
C
C init=PASS ms=4 error=0x00 NONE data=0x00 type=3
```

### Consequence

This run contradicts a simple one-way model in which W5100 activity poisons subsequent SD access. Under this power condition, SD initialization fails immediately after startup but succeeds after the LAN phase.

The result makes **power-up sequencing / rail settling / elapsed-time effects** materially plausible. It does not yet prove that LAN activity is the cause of recovery, because LAN startup also introduces additional elapsed time and SPI activity.

### Next minimal discriminator

On a fresh power-up with the same additional-power arrangement, do **not** start LAN. Wait approximately the same amount of time that the successful LAN phase previously consumed, then issue only `C`.

- If delayed `C` passes: startup/power settling is favored.
- If delayed `C` still fails but `L1 -> L0 -> C` passes: LAN/W5100 activity itself becomes the next candidate.
