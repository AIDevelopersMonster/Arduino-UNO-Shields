# TEST-11B — Sd2Card low-level init after LAN: observed result

**Date:** 2026-10-11  
**Status:** **VALID SD BASELINE / LAN STAGE STALLS**

Observed sequence:

```text
C
C init=PASS ms=304 error=0x00 NONE data=0x00 type=3
C
C init=PASS ms=4 error=0x00 NONE data=0x00 type=3
L1
L1 prepareLAN: OK
L1 W5100 soft reset: PASS
```

No later `L1 LAN PASS` or `L1 DHCP: FAIL` was observed. Subsequent typed commands (`L0`, `C`, `R`, ...) produced no responses because the sketch had not returned to its command loop.

## What this establishes

- The low-level Arduino `Sd2Card::init()` baseline is valid and repeatable before LAN.
- SDHC card type 3 was detected twice with native error code 0.
- Raw W5100 MR software reset still succeeds after the SD low-level initialization.
- The sketch then stalls somewhere after that point inside the normal Ethernet startup path, before it can print the result of `Ethernet.begin(...)`.

This run does **not** test SD after LAN because LAN startup never returned and `L0` was never executed.

## Next isolation step

Before adding another full network test, use the existing command set after a fresh AVR reset:

```text
C
R
C
```

If both C probes pass, raw W5100 reset alone does not poison subsequent SD initialization. The remaining fault boundary then lies inside later Ethernet/W5100 initialization or socket/DHCP activity.


## Additional-power run

The operator repeated TEST-11B with additional power connected. The behavior inverted relative to the earlier run:

```text
C
C init=FAIL ms=2005 error=0x01 CMD0 data=0xFF
C
C init=FAIL ms=2004 error=0x01 CMD0 data=0xFF
L1
L1 prepareLAN: OK
L1 W5100 soft reset: PASS
L1 LAN PASS IP=192.168.1.79
UDP=5006
L0
L0 UDP stop + LAN release: DONE
C
C init=PASS ms=4 error=0x00 NONE data=0x00 type=3
```

### Consequence

This run contradicts a simple one-way model in which W5100 activity poisons subsequent SD access. Under this power condition, SD initialization fails immediately after startup but succeeds after the LAN phase.

The result makes **power-up sequencing / rail settling / elapsed-time effects** materially plausible. It does not yet prove that LAN activity is the cause of recovery, because LAN startup also introduces additional elapsed time and SPI activity.

### Next minimal discriminator

On a fresh power-up with the same additional-power arrangement, do **not** start LAN. Wait approximately the same amount of time that the successful LAN phase previously consumed, then issue only `C`.

- If delayed `C` passes: startup/power settling is favored.
- If delayed `C` still fails but `L1 -> L0 -> C` passes: LAN/W5100 activity itself becomes the next candidate.


## Extended additional-power run: state-dependent behavior

A longer run under the same additional-power condition showed that neither direction is deterministic.

Observed groups included:

1. Startup SD low-level init failed twice at CMD0 (`data=0xFF`), LAN then passed, and the following SD init passed in 4 ms.
2. Later, two consecutive SD init probes passed (3-4 ms), LAN passed, and the following two SD init probes failed at CMD0 (~2004-2005 ms).
3. In another LAN cycle, the first DHCP attempt failed, a subsequent LAN attempt passed at the same IP `192.168.1.79`, and two following SD init probes both passed in 4 ms.

### Revised conclusion

The previous deterministic model "LAN use poisons SD until AVR reset" is rejected by this extended log.

The defect is **state-dependent / intermittent** in the shared SPI system. Both of these have now been observed under additional power:

- LAN followed by SD PASS.
- LAN followed by SD CMD0 FAIL.

Likewise, LAN itself may fail on one attempt and pass on the next.

Additional power therefore does not eliminate the fault; it changes the observed state sequence. This materially increases the plausibility of one or more of:

- shared-SPI electrical interaction / MISO release or biasing,
- device-specific power-up or reset sequencing,
- card-specific SPI behavior,
- timing-sensitive interaction between W5100 and microSD on this clone shield.

It weakens a purely deterministic high-level-library lifecycle explanation.

### Recommended next discriminator

Before further library complexity, repeat the exact TEST-11B command sequence with the second microSD card already available on the bench, keeping firmware, shield, power arrangement and cabling unchanged. If the failure pattern follows the card, prioritize SD-card electrical/protocol compatibility. If both cards show the same intermittent pattern, prioritize shield/W5100/shared-bus hardware behavior.


## Second microSD card run

With a different microSD card installed, the observed behavior changed again:

- Multiple low-level `Sd2Card::init()` probes passed consistently in 3-395 ms with error 0x00, type 3.
- Every observed `L1` attempt reported `W5100 soft reset: FAIL`.
- DHCP also failed on those attempts.
- A standalone `R` W5100 software reset also failed.
- SD low-level probes continued to pass after failed LAN attempts.

### Significance

Changing only the microSD card materially changed which peripheral could communicate reliably on the shared SPI bus. This is strong evidence for card-dependent electrical/protocol interaction on the shared bus (especially MISO/CS behavior or loading), rather than a deterministic software-only lifecycle bug.

It does not yet prove that the card actively drives MISO while deselected. A static tri-state/bias test with both CS lines HIGH and card-out/card-in comparison is the next bounded discriminator.
