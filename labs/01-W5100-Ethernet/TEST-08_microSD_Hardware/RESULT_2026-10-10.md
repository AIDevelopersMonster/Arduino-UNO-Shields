## Repair prepared for a new hardware run

Source review identified a missing shared-bus handoff in the sketch: after SD
operations, the raw Ethernet helpers selected W5100 without first clocking an
idle byte while both D4 and D10 were HIGH. Arduino SD 1.3.0 `chipSelectHigh()`
deselects the card and ends its SPI transaction without this extra byte.
The upstream SdFat `spiStop()` clocks FF after deselection; this supports the
handoff repair, but does not establish the cause of this particular shield's FAIL.

Firmware **0.2** adds the idle byte before every W5100 selection, logs two actual
RTR readings plus the expected value after SD, and records the initial probe/restore.
There is no retry until success, W5100 reset, post-SD RTR rewrite or relaxed
preservation criterion. A blank line separates startup bytes from the BOOT banner.
Host **0.2** still requires exactly one correctly framed BOOT, all 15 checks and
matching RTR diagnostics; it rejects old firmware before sending RUN.

Development validation: actual new AVR 1.8.6 compilation passes at 14,134 B Flash /
1,050 B static SRAM; 29 host verdict cases pass. A compiled peripheral model
using the actual sketch's SPI helpers passes v0.2 and rejects v0.1 under its
declared SD-MISO-release condition. These are development results, not hardware proof.

The unchanged v0.2 host verdict module rejected the supplied console for the
RTR discrepancy, missing final RAM stage and terminal FAIL. The after-SD
diagnostic only reads RTR; it does not rewrite it, reset W5100, vote over reads
or replace the first response with the second. A discrepancy in returned
data is not proof that the hardware register permanently changed, nor proof
of a particular noise source. The generic leftover-file warning does not
override the explicit successful cleanup in this run.

Timing or shared-MISO signal integrity is a plausible hypothesis, consistent
with the operator's observation. WIZnet's [W5100 datasheet, SPI Timing, p.67](https://docs.wiznet.io/assets/files/W5100_DS_V128E-68b8612e5ec92bb4cdf8f53cf6bfb8a9.pdf)
declares SCLK, select and input/output timing requirements. The log cannot
measure these waveforms, voltage levels, contact quality or supply ripple.
CMD0 timeout and RTR discrepancy are distinct observations; a common cause
has not been established.

## Prepared v0.3 diagnostic: W5100 SPI 4 MHz -> 1 MHz

Only the W5100 helper clock setting changes in the device's test behavior,
including its deselected idle byte. SPI mode/order, CS pins, number of idle
clocks, initial write/probe/restore, both post-SD reads, payload and all 15
acceptance gates remain the same. No additional delay, automatic init retry,
post-SD RTR write or majority voting is added. SD 1.3.0 remains at 250 kHz
during init and 4 MHz for data operations with SPI_HALF_SPEED. Thus the
frequency diagnostic targets the W5100/handoff discrepancy; it does not lower
the SD init clock that already produced CMD0 timeouts.

Firmware/runner version 0.3 and `eth_spi_hz=1000000` in BOOT distinguish this
condition from v0.2. The build and run summaries record all three clock settings;
source/HEX hashes and strict version/frequency gates prevent treating old
firmware as the new condition. The new runner requires a fresh build/upload.
Earlier v0.2 logs remain historical evidence validated by their own module
version, not by changing their BOOT lines to fit v0.3.
