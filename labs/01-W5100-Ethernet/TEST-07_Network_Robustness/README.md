# TEST-07 — Network Robustness / UNO + W5100

**Статус: BUILD VERIFIED / Baseline и повторный Cable PASS / пять сценариев PENDING.**
Дата подготовки: 2026-10-09. [Аппаратный Baseline от 2026-10-10](RESULT_2026-10-10.md)
завершился с `RESULT PASS`. Первый Cable завершился FAIL; повторный Cable — PASS.
Эти аппаратные результаты относятся к первоначальному runner. Пошаговый host runner
**0.2** проверен отдельно на модели: [проверки разработки](VALIDATION_GUIDED_2026-10-10.md).
Полный TEST-07 FULL PASS пока не подтверждён.
TEST-05/06 сохраняют свои собственные результаты; они не подтверждают устойчивость
новой прошивки. Этот тест использует оба их протокола одновременно.

## Аппаратура и протоколы

ATmega328P / Arduino UNO; синий Ethernet Shield W5100; Ethernet CS=D10;
microSD вынута, SD CS=D4 постоянно HIGH; SPI через ICSP; UART 115200, 8N1.
MAC TEST-07: `02:4B:4F:4E:51:07` (отличается от TEST-05/06).

| Сервис | Протокол |
| --- | --- |
| UDP :5001 | Побайтовое бинарное эхо 1–128 байт отправителю; большие пакеты отбрасываются |
| TCP :5000 | `payload + LF` → `ECHO payload + LF`, до 64 байт; один запрос и закрытие; CR пропускается |
| UART | `EVT`, `STAT`, `INFO`; `?` запрашивает STAT; `D` вручную запускает новый DHCP |

У W5100 физический линк через `Ethernet.linkStatus()` **Unknown**. Это не ошибка
и не доказательство наличия кабеля. Для Cable сценария нужны отметки оператора,
неудачные пробы во время разрыва и точный обмен после восстановления.
Потеря питания роутера и недоступность DHCP — отдельные причины, не равные
физическому разрыву линка. Отсутствие входящих пакетов само по себе не вызывает
перезапуск сети: тихая исправная сеть допустима.

## Что делает новая прошивка

1. `setup()` инициализирует UART/CS. Первая DHCP-попытка выполняется в `loop()`.
2. `Ethernet.begin(mac,6000,1000)` запрашивает аренду. После неудачи новая попытка
   начинается через 5 секунд **после завершения** предыдущей. Статического IP нет.
3. После успеха создаются UDP-сокет и TCP-слушатель. DHCP `maintain()` вызывается
   примерно раз в секунду; TCP читается небольшими порциями без ожидания всей строки.
4. `maintain()` rc=1/3: запись ошибки, закрытие приложений/сокетов, сброс IP в
   0.0.0.0 и новое получение аренды. rc=2/4: запись результата и конфигурации;
   при смене IP сервисы пересоздаются. Клиент на ПК узнаёт новый IP из UART.
5. Незавершённый/молчаливый TCP-клиент закрывается за 1500 мс плюс время блокирующих
   вызовов библиотеки. Используется `server.accept()`, чтобы увидеть и клиента,
   который подключился, но не отправил ни байта. Один активный TCP-клиент.
6. Статистика раз в 5 секунд: uptime, IP, ready, DHCP-попытки/результаты, счётчики
   UDP/TCP, sampled SRAM, максимальная наблюдённая длительность DHCP-вызова.
   Каждый пакет не печатается в UART: журнал не должен быть основной нагрузкой.

`begin()`/`maintain()` — **синхронные** функции Ethernet 2.0.2. Значения 6000/1000
задают тайм-ауты DHCP, но не строгую верхнюю границу всего вызова: библиотека
может завершать ответ, выполнять ARP и в одном `maintain()` делать renew и rebind.
В это время эхо/UART-команды не обслуживаются. `max_dhcp_ms` показывает измеренный
максимум. RTR=200 мс, RCR=2 ограничивают повторные передачи чипа. Это не защита от
зависания SPI/самого W5100. Watchdog и аппаратный reset W5100 здесь не заявлены.

## 1. Получить, собрать, загрузить

Windows / **PowerShell 7 (`pwsh`)**, Arduino CLI. Ветка с реализацией:
`feature/w5100-test07-network-robustness`. После merge можно использовать `main`.
Перед checkout завершите/сохраните собственные локальные изменения обычным способом.

```powershell
cd C:\GitHub\Arduino-UNO-Shields
git fetch origin
git switch feature/w5100-test07-network-robustness
git pull --ff-only
arduino-cli core update-index
arduino-cli core install arduino:avr@1.8.6
arduino-cli lib update-index
arduino-cli lib install "Ethernet@2.0.2"
$test = ".\labs\01-W5100-Ethernet\TEST-07_Network_Robustness"
& "$test\Build-Test07.ps1" -UploadPort COM4
```

Build helper проверяет **фактически выбранные** core 1.8.6 или 1.8.8 и Ethernet 2.0.2.
На уже установленной 1.8.8 менять core не требуется: сборка на ней подтверждена
пользователем (20 392 B Flash, 879 B static SRAM). Версия в отчёте берётся из
реальной сборки, а не подставляется как константа.
Если другая копия Ethernet перехватила include, сборка будет отклонена.
`build\TEST07\compile.json` сохраняет вывод компилятора и выбранные библиотеки;
`build-summary.json` — размеры, версии и SHA256 HEX/исходников. Измеренный HEX
загружается через `--input-dir`, повторная скрытая компиляция не нужна.

Если компиляция уже успешно завершилась, но старый helper отклонил core 1.8.8,
после обновления скрипта можно завершить проверку и загрузить готовый HEX:

```powershell
git pull --ff-only
& "$test\Build-Test07.ps1" -UseExistingBuild -UploadPort COM4
```

`-UseExistingBuild` читает существующий `compile.json`, проверяет успех, каталог,
версии и память, требует наличия HEX и отклоняет исходник firmware с датой новее
бинарника/отчёта. Эта проверка по времени файлов не является криптографической
проверкой соответствия исходника HEX; используйте её только для своей только что
выполненной сборки. Обычный режим остаётся сборкой с сохранением отчёта.

Эквивалентные явные команды:

```powershell
arduino-cli compile --fqbn arduino:avr:uno --warnings all --build-path .\build\TEST07 $test
if ($LASTEXITCODE -ne 0) { throw "Compile failed" }
arduino-cli upload -p COM4 --fqbn arduino:avr:uno --input-dir .\build\TEST07 $test
if ($LASTEXITCODE -ne 0) { throw "Upload failed" }
```

Для итоговой сертификации используйте build helper, чтобы получить JSON с memory gate.
Закройте Arduino IDE Serial Monitor, Arduino CLI monitor и другие владельцы COM4.
Не фиксируйте прежний DHCP IP: runner получает актуальный адрес из UART.

## 2. Первые проверки — Baseline, затем Cable

```powershell
& "$test\Test-NetworkRobustness.ps1" -SerialPort COM4 -Scenario Baseline -DurationSeconds 60
& "$test\Test-NetworkRobustness.ps1" -SerialPort COM4 -Scenario Cable -DurationSeconds 180
```

Runner открывает COM с DTR=true; UNO обычно перезапускается. Он должен увидеть
ровно один `BOOT`, `INFO test=07 version=0.1`, W5100, STAT и три точных UDP-ответа.
До 30 секунд выделено на начальный healthy warmup. Если авто-reset не сработал,
нажмите RESET **сразу после открытия COM**, до начала проверки сервиса. Повторный
RESET во время испытаний делает результат FAIL; восстановление должно быть автоматическим.

### Пошаговый Cable — действия только по приглашению

1. **ШАГ 1: ОСТАВЬТЕ соединение исправным.** Скрипт сам проверяет минимум
   20 s healthy, 24 UDP, четыре длины и три TCP. Ошибка исходного обмена
   показывается сразу и останавливает сценарий до приглашения отключить.
2. **ШАГ 2: СЕЙЧАС ВЫНЬТЕ Ethernet-кабель.** Вынуть из UNO, USB оставить.
   D/R не нужны. Скрипт ожидает три последовательные неудачные пробы.
   Если за 60 s устойчивый разрыв не обнаружен, действие не подтверждено: FAIL.
3. **Отказ подтверждён; идёт автоматическая выдержка.** Кабель остаётся вынутым.
   Скрипт отсчитывает 15 s от первой завершившейся неудачной пробы в подтверждённой
   последовательности. Возврат точного эха до приглашения подключить даёт FAIL.
4. **ШАГ 3: СЕЙЧАС ПОДКЛЮЧИТЕ Ethernet-кабель.** Вставить кабель обратно.
   Возврат обмена определяется автоматически, R не нажимается.
5. **ШАГ 4: ОБМЕН ВОССТАНОВЛЕН.** Оставить соединение исправным до `RESULT`.
   POST требует 24 UDP и три TCP; прогон продолжается до заданной длительности.

`ПРОГРЕСС` показывает фазу, UDP/TCP, ошибки, outage-пробы, остаток выдержки и
времени прогона. Оператор не отсчитывает секунды. Q прерывает тест с FAIL.
RESET во время отказа/восстановления запрещён.

**Время восстановления runner 0.2:** окно 45 s начинается с `RESTORE_REQUESTED`
и включает реакцию оператора. `RecoveryMs` — от приглашения подключить до первого
из трёх последовательных точных UDP-ответов. Это полное время этапа по скрипту,
а не PHY latency. При выполнении действия после приглашения оно является
консервативной границей для возврата обмена после действия.
`recovery_timing_origin` записывается в JSON; прежние значения от ручной R
с этим измерением не смешиваются.

### StartupDhcp — подготовка по приглашению

После запуска скрипт сначала просит вынуть кабель и подтвердить **Enter**.
На подготовку выделяется 60 s; COM ещё закрыт, часы аппаратного прогона ещё не
запущены. Затем открывается COM, фиксируется BOOT, ожидается реальный DHCP_FAIL
и автоматически отсчитывается выдержка. Подключать только по **ШАГ 3**.

Для терминала без Enter задайте пустой `-MarkerFile`; после извлечения добавьте
в него `READY` из другого терминала. В Cable файл не требуется.
D/R ни в одном сценарии не переключают фазы. Команда UART D — отдельный ручной
DHCP из прошивки; она делает сертификацию автоматического восстановления FAIL.

Параметры runner: UDP интервал 100 мс
**после** завершения предыдущей пробы, тайм-аут 1000 мс. Это последовательная
нагрузка до примерно 10 проб/с, не обещание 10 pps при отказах. UDP-сокет каждой
пробы новый, поэтому задержанный ответ предыдущего запроса не может пройти
как следующий ответ; проверяются адрес/порт источника, длина и каждый байт.
Для 16/64/128 байт включены ID сеанса и номер запроса. В каждой healthy/POST фазе
чередуются 1,16,64,128 байт. TCP проверяется каждые 5 секунд, включая 64 байта и EOF.

## 3. Полная матрица сценариев

Каждый сценарий запускается отдельно; новый запуск/reset начинается до fault,
внутри recovery перезапуск платы запрещён. PowerShell скрипты не отключают NIC,
не управляют роутером и не меняют firewall. Обеспечьте доступ UDP 5001 / TCP 5000
в используемой локальной сети.

| Scenario | Запуск / действия | Дополнительное условие PASS |
| --- | --- | --- |
| Baseline | Кабель подключён, DHCP работает; 60–120 с | 24+ UDP, все 4 длины, 3+ TCP без ошибки |
| Cable | 180 с; выполнять ШАГ 2/3, выдержку считает скрипт | Три последовательных failed-пробы; выдержка 15 s; возврат эха <=45 s от приглашения; POST |
| StartupDhcp | 180 с; вынуть по первому приглашению/Enter, подключить по ШАГ 3 | Initial DHCP_FAIL до приглашения; автоматический DHCP; возврат эха <=45 s от приглашения; POST |
| DhcpRenew | Изолированная DHCP-сеть с арендой 120–300 с; 600 с, ничего не отключать | Настоящий `DHCP_MAINTAIN rc=2`, здоровый обмен; rc=0 или новый `DHCP_OK` не засчитывается |
| DhcpOutage | Изолированная сеть с короткой арендой; 600 с; отключить DHCP по ШАГ 2, включить по ШАГ 3 | Естественный maintain rc=1/3 до приглашения; подтверждённый отказ; автоматическая аренда и POST |
| Soak | Нормальная сеть; 600 с, при желании 1800/3600 с | Run >=600 с, healthy >=540 с; ноль ошибок здорового обмена, UART/RAM/reset gates |
| TcpAbort | Нормальная сеть; 90 с | 5 незавершённых TCP-запросов с RST, 5+ rejection на плате; продолжение корректных UDP/TCP |

```powershell
# Подготовку и момент подключения задаст сам скрипт:
& "$test\Test-NetworkRobustness.ps1" -SerialPort COM4 -Scenario StartupDhcp -DurationSeconds 180
# После настройки короткой аренды на отдельной тестовой сети:
& "$test\Test-NetworkRobustness.ps1" -SerialPort COM4 -Scenario DhcpRenew -DurationSeconds 600
& "$test\Test-NetworkRobustness.ps1" -SerialPort COM4 -Scenario DhcpOutage -DurationSeconds 600
# Нормальная сеть:
& "$test\Test-NetworkRobustness.ps1" -SerialPort COM4 -Scenario Soak -DurationSeconds 600
& "$test\Test-NetworkRobustness.ps1" -SerialPort COM4 -Scenario TcpAbort -DurationSeconds 90
```

При длинной штатной аренде `DhcpRenew` может не увидеть продления за 600 с:
результат **FAIL: renewal evidence absent**, а не отрицательное заключение о DHCP.
Увеличьте длительность до нужного T1 или используйте короткую аренду на отдельной
тестовой сети. Зафиксируйте lease/T1/T2 из DHCP-сервера/захвата: публичный API
Ethernet 2.0.2 этих величин не раскрывает. rc=2 — успешная renew-процедура
библиотеки; rc=4 — rebind. Для проверки протокольной последовательности полезен
Wireshark с фильтром `udp.port == 67 || udp.port == 68` на интерфейсе/зеркальном порту,
где доступны DHCP-пакеты. Захват только на ПК не всегда видит чужой unicast.

Не имитируйте natural renewal командой UART `D`: это лишь новый `begin()`.
Смена IP обрабатывается прошивкой и runner, но не сертифицируется автоматически:
для отдельного IP-change результата нужно фактически получить `IP_CHANGED` и
выполнить обмен по новому IP. Перезагрузка роутера, длительный разрыв (120+ с)
и три повторения Cable полезны как дополнительные протоколы; базовый FULL PASS
не означает, что все длительности/варианты fault уже испытаны.

## 4. Объективные критерии и границы

- Build gate: Flash **<=29 000/32 256 B**, статическая SRAM **<=1200/2048 B**,
  core/Ethernet заданных версий. Это запас на дальнейшие изменения, не измерение стека.
- UART: ровно один наблюдённый BOOT; ожидаемый firmware banner/W5100; >=2 STAT;
  uptime не уменьшается. Пропущенный BOOT — недостаточно доказательств, FAIL.
- `min_free >=512 B`, падение сопоставимого sampled `free` от первого healthy
  STAT не более 64 B. Это выборочные stack-to-heap показания, **не** истинный
  максимум использования стека внутри DHCP/драйвера. Нет `String`/malloc в коде приложения.
- Все healthy/POST запросы должны пройти; ноль подмен/повреждений/неверных длин
  **в любой фазе**. Ноль firmware drop; ошибки отправки во время outage допустимы
  и записываются; в healthy/POST они дают FAIL. Потери warmup/outage/recovery
  сохраняются отдельно и не объявляются «0% потерь за весь тест».
- Cable/StartupDhcp/DhcpOutage: реальные fault-признаки по таблице, >=10 с outage
  (пошаговая выдержка 15 s), три точных ответа в пределах 45 s от приглашения, POST.
  Преждевременное подключение или отсутствие приглашения восстановить дают FAIL.
- Каждый сценарий завершается PASS/FAIL и кодом 0/1. Отсутствующее обязательное
  событие даёт FAIL за недостатком подтверждения. Ctrl+C/остановленный процесс не
  является завершённым измерением; оценивайте только полный `summary.json`.
- Подготовка StartupDhcp отдельно ограничена 60 s. Период whole-run ограничен
  `DurationSeconds` (максимум 86400). Последняя UDP
  проба ограничивается остатком времени; окончание TCP/COM/запись файлов могут
  добавить несколько секунд. Это не жёсткий realtime deadline операционной системы.

Один сценарий PASS — результат только этого сценария. **FULL PASS** возможен
после семи завершённых аппаратных сценариев + build gate, на одной и той же плате
с одинаковыми исходниками. Не смешивайте результаты разных версий/образцов.

```powershell
# Подставить семь фактических путей summary.json, по одному на сценарий:
$summaries = @(
  "$test\runs\<Baseline-run>\summary.json",
  "$test\runs\<Cable-run>\summary.json",
  "$test\runs\<StartupDhcp-run>\summary.json",
  "$test\runs\<DhcpRenew-run>\summary.json",
  "$test\runs\<DhcpOutage-run>\summary.json",
  "$test\runs\<Soak-run>\summary.json",
  "$test\runs\<TcpAbort-run>\summary.json"
)
& "$test\Get-Test07Certification.ps1" -BuildSummary .\build\TEST07\build-summary.json `
  -ScenarioSummary $summaries -Sample "UNO + blue W5100, мой образец №1"
```

Пути с `<...>` — только placeholders, их заменяют фактическими каталогами.
Aggregator перепроверяет метрики, полноту набора, одинаковый COM и SHA256
исходников/host кода. Он не доказывает, что оператор действительно вынимал кабель
или загрузил именно сохранённый HEX: сохраните вывод загрузки и идентификацию
образца. Исходный код firmware на плате выводит версию, а не криптографическую аттестацию.

Перед `git pull` завершите текущий прогон. Firmware при переходе на runner 0.2
сохранена; повторная загрузка не нужна. Обновить build hashes можно без компиляции:
`& "$test\Build-Test07.ps1" -UseExistingBuild`.
Исторические PASS runner 0.1 остаются в отчёте. Для единого комплекта runner 0.2

## Журналы и диагностика

Каждый запуск создаёт отдельную папку `runs/<date>-<scenario>-<id>/`:

- `serial.log`: UTC ПК + дословные строки устройства, включая DHCP-коды.
- `events.jsonl`: UART-события, fault-отметки, ошибки и начало/конец запуска.
- `probes.csv`: каждая проба, фаза, транспорт, IP, длина, результат и RTT.
- `summary.json`: причины PASS/FAIL, SRAM, recovery, количества, hashes.

Для одного только наблюдения (закрыть runner, иначе COM занят):

```powershell
& "$test\Watch-NetworkEvents.ps1" -SerialPort COM4 -DurationSeconds 120
```

Logger сам не оценивает PASS. UART `?` безопасно запрашивает статистику. UART `D`
полезен для диагностики, но любой такой вызов в аппаратном сценарии запрещает
автоматический recovery PASS. ICMP/ping можно использовать дополнительно, но
он не заменяет проверку UDP/TCP и целостности.

`runs/` и `build/` исключены из git. Для публикации результата выберите законченные
журналы, добавьте вручную в каталог evidence и заполните `RESULT_TEMPLATE.md`.
Сохраните все неудачные попытки, причину повтора и фактические параметры сети.

Источники поведения библиотеки: [Ethernet 2.0.2 API](https://github.com/arduino-libraries/Ethernet/blob/2.0.2/docs/api.md),
[Dhcp.cpp](https://github.com/arduino-libraries/Ethernet/blob/2.0.2/src/Dhcp.cpp),
[Ethernet.cpp](https://github.com/arduino-libraries/Ethernet/blob/2.0.2/src/Ethernet.cpp),
[EthernetServer.cpp](https://github.com/arduino-libraries/Ethernet/blob/2.0.2/src/EthernetServer.cpp).

Этот комплект проверяет LAN recovery и ограниченную нагрузку конкретного образца;
он не сертифицирует работу сутками, безопасность, интернет, microSD, сохранение
данных при отключении питания или автоматическое устранение аппаратного зависания.
